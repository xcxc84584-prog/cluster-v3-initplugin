# Cluster-v3 initplugin API / Event LOG audit (2026-11-21)

Scope: Explorer v2.4.0, BasicTextEditor v2.9.0 and Workspace message
bridge, reviewed against Cluster-v3 Host's current logging implementation.

## Result: NOT complete

The Host core has a ring of the latest 2,000 LOG entries, persistent ELOG and
Router.request success/error records. This DOES NOT mean every plugin-to-Host
API interaction and local workspace event is recorded.

| Path | Request / event | Current log coverage | Gap |
| --- | --- | --- | --- |
| Host Router.request | Registered cross-plugin call | Host logs success or ELOG failure | Kernel entry is not guaranteed to contain complete request/response payload |
| Plugin direct PRMU / PMU / Contract calls | Host bridge dispatch | Failures are logged as ELOG | Successful non-Router calls are not individually logged |
| Explorer hostRequest | cluster.plugin.v1 request and response | Host can log selected operations | Not every success, timeout and response has a correlated plugin-level entry |
| Editor internal request | cluster.editor.v1 req/rep | Router may see original request | Workspace relay and internal replies have no systematic LOG |
| Editor document events | document.opened/changed/saved/closed, tab.activated | Events are emitted to Workspace/Explorer | Most events are not sent to Host LOG |
| Explorer workspace events | delete.confirm, external.changed, disk.reconnected | UI message relay | No guaranteed event audit entry |
| Workspace File bridge | save-request/save-result | Errors reach UI but not all Host logs | No guaranteed correlated duration/status record |
| Local persistence | IndexedDB snapshot/restore | Some errors become workspace.error | Successful local persistence not in LOG |

Evidence in source:
- `plugins/cluster.explorer/scripts/explorer.js`: `hostRequest`,
  `sendWorkspace`, workspace file message handlers.
- `plugins/cluster.text-editor/modules/editor/scripts/editor.js`:
  `emitEditorEvent`, `handleEditorRequest`, `saveViaExplorer`.
- `plugins/cluster.text-editor/scripts/workspace.js`: message forwarding
  and progress/event handling; no universal PMU.log emission.
- `Cluster-v3/src/core/plugin-kernel.js`: Router.request logging, ring
  storage and persistent ELOG.
- `Cluster-v3/src/plugin/browser-runtime.js`: errors logged to ELOG.
- `Cluster-v3/src/plugin/host-bridge.js`: public `PMU.log` transport
  exists for authenticated plugin calls.

## Recommended remediation (not included in this audit)

1. Introduce a single trace envelope for every request and reply:
   `requestId`, `traceId`, source, destination, action, status,
   timestamp, duration and error code.
2. Audit successful Host-bridge calls **at the trusted Host ingress**
   (rather than trusting a plugin to self-report). Never log full file
   contents, secrets or tokens.
3. For local postMessage traffic, add bounded plugin-generated event
   metadata logging through `PMU.log`; accept that untrusted plugin
   self-reporting is not a tamper-proof security audit.
4. Ensure every request has at most one terminal success/error log record
   correlated by `requestId`, with timeouts treated as failures.
5. Add end-to-end tests for request-reply correlation, failure recovery,
   local file events and event volume/backpressure.

**Important:** The pagination introduced in Cluster-v3's LOG UI limits DOM
rendering to one page. The current Host kernel still restores all historical
ELOG entries into memory during startup. Full database-level cursor pagination
requires an additional Host logging/storage change beyond the authorized
LOG page UI scope.
